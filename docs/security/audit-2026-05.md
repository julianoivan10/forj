# Forj Security Audit — May 2026

> Internal pre-mainnet audit. Treats the platform as adversarial: assumes
> the website / database / arbiter could be malicious and asks "what can
> a user lose, and how?" Trust is the core promise of Forj — this
> document is the answer to "prove it."
>
> Scope:
>   - Smart contract: `packages/contracts/contracts/ForjEscrow.sol`
>   - Backend: `packages/api/src/**`
>   - Frontend: `apps/web/**`
>   - Operations: env, deploy, multisig, recovery
>
> Out of scope: third-party services (Privy, Pimlico, Neon, UploadThing,
> Resend) — each has its own audit history; we trust them as components
> and contain blast radius via least-privilege keys.

---

## TL;DR — trust model

**What Forj CAN do (acceptable):**
- Refuse a user account (auth gate, soft-delete).
- Hide contracts from search / listings.
- Change UI copy, branding, fees on future escrows.
- Resolve disputes — but only after either party flags one (`raiseDispute`).
- Email users.

**What Forj CANNOT do (enforced by contract):**
- Move USDC out of a funded escrow without going through one of the
  defined paths (`release`, `refund`, `claimAfterTimeout`, `resolveDispute`).
- Change the fee on a funded escrow (snapshotted at fund time).
- Resolve a dispute that wasn't raised by a party.
- Block a freelancer from claiming after the 7-day auto-release window.
- Withdraw arbitrary tokens from the contract.
- Re-route fees to a different recipient on a funded escrow (recipient
  is per-contract, set at deploy; can be changed for FUTURE releases only).
- Pause withdrawals (only `fund()` is pausable).

**What could go wrong (with severity):**
- Owner key compromise → Critical (can siphon future fees, can pause new
  funding). Mitigation: multisig.
- Fee recipient EOA compromise → High (drains accumulated fees that
  haven't been swept). Mitigation: multisig + frequent sweeps.
- Backend bug rejecting valid txs → Medium (creates orphan escrows;
  recoverable via Basescan refund / dispute). Mitigated in current
  release by relaxed verifier + double-fund guard.
- Frontend showing wrong wallet address → Medium (user sends to wrong
  address). Mitigated by `useCanonicalWallet`.
- Privy session hijack → Critical (account takeover, full impersonation).
  Mitigated by Privy's HttpOnly cookies + JWT signatures. Out of our control.

## 1. Smart contract findings (ForjEscrow.sol v2)

### Strengths

- ✅ `nonReentrant` on every state-mutating + value-moving function.
- ✅ `SafeERC20` wraps every `transfer` / `transferFrom` — handles USDC
  and any future non-standard ERC-20 we add.
- ✅ `Ownable2Step` — two-step ownership transfer prevents accidental
  loss to a wrong address (e.g. miskeyed multisig migration).
- ✅ State changes BEFORE external calls in all paths (CEI pattern).
  Even with `nonReentrant`, this is belt-and-braces.
- ✅ Solidity 0.8.24 — built-in overflow checks. No `unchecked` blocks.
- ✅ `Pausable` only on `fund()`. Critically, **withdrawals are NEVER
  pausable** — even if the platform multisig is compromised + paused,
  users can still recover their funds via `release` / `refund` /
  `claimAfterTimeout`.
- ✅ Fee bps capped at `MAX_FEE_BPS = 1000` (10%) per side — owner can't
  silently set 99% fees.
- ✅ Per-escrow fee snapshot (`platformFeeBps` per row) — changing
  `defaultFees` doesn't retroactively affect funded escrows.
- ✅ Refund returns FULL deposit (`amount + clientFee`) — platform takes
  no fee on mutual cancellation.
- ✅ `nextEscrowId` starts at 1; `Status.None = 0` is sentinel for
  uninitialised slots in the mapping.

### Findings

| ID | Severity | Issue | Mitigation |
|---|---|---|---|
| **SC-01** | **High (for mainnet)** | `feeRecipient` is currently an EOA, not a multisig. Single key compromise = drain of all accumulated fees that haven't been swept. | Migrate to Safe multisig BEFORE mainnet. Safe wallet `0x2332…D5e6` is already created — needs activation + ownership transfer. |
| **SC-02** | **High (for mainnet)** | Contract `owner` is currently the deployer EOA `0xa3b1d4ad…71052`. Owner can: pause funding (DoS new escrows), call `resolveDispute` on disputed escrows, change `feeRecipient`, change `defaultFees`. | Same: migrate ownership to multisig. Use Ownable2Step's two-step transfer — pending owner must `acceptOwnership` from the multisig itself. |
| **SC-03** | Medium | `setFeeRecipient` has no timelock. Owner can divert future fees instantly. | Add 24h timelock contract between owner and escrow (or live with the trust assumption — multisig + transparency mitigates much of it). |
| **SC-04** | Medium | `resolveDispute` requires `sum === amount + clientFee`. Off-by-one from integer rounding will revert. | Frontend admin UI MUST compute split server-side from on-chain `getEscrow(id).amount + .clientFee`. Never let arbiter type amounts manually. |
| **SC-05** | Low | Frontend computes `clientFee` locally before `fund()`. If owner changes `defaultClientFeeBps` mid-flight, the approve amount might be too low → `transferFrom` reverts on insufficient allowance. | Frontend should call `quoteFund(amount)` view to get authoritative figure at submit time. (Low because changing default fees is owner-only and rare.) |
| **SC-06** | Low | Anyone can send arbitrary ERC-20 tokens directly to the contract address. They're permanently stuck — no rescue function. | Add `rescueToken(IERC20 token, address to, uint256 amount)` admin function that **excludes USDC**. Or document this as known. |
| **SC-07** | Info | `block.timestamp` used for auto-release timing. Miners can manipulate by ~12s. | Negligible — 7-day window vs 12s manipulation. No action needed. |
| **SC-08** | Info | No upgrade mechanism. Bugs require redeploy + migration. | Intentional — upgradeable contracts have their own attack surface (proxy admin compromise). Redeploy is the right model for a financial primitive. |
| **SC-09** | Info | Disputed escrows freeze indefinitely. If owner never resolves, funds stay locked. | Acceptable: contract design treats arbiter as a service the platform commits to providing. A neglectful arbiter is a reputational problem, not a contract bug. |

### Recommended additions before mainnet

1. **`rescueToken()`** to recover misdirected tokens (SC-06).
2. **`getEscrows(uint256[] ids)`** batch view for analytics / frontend
   bulk reads. Not security, performance.
3. **Optional**: per-escrow `freelancerFee` override (not just default).
   Lets premium freelancers negotiate lower fees individually.

## 2. Backend security audit

### Auth boundary

`getUserFromToken` (`apps/web/lib/privy/server.ts`):
- Reads Privy cookie, verifies signature cryptographically (not just
  presence check).
- Resolves to a DB user — auto-provisions on first login.
- Returns `null` for soft-deleted accounts (tombstoned `deletedAt`)
  — prevents zombie logins.
- Picks canonical wallet (smart wallet > embedded EOA > linked
  external).

**Finding BE-01 [Info]**: Auto-sync of `walletAddress` on every login
rewrites the DB if Privy now exposes a different canonical wallet.
This is intentional (smart-wallet migration) but means: **if a user
ever connects a new external wallet via Privy that becomes their
canonical**, their DB `walletAddress` flips. Past escrows still use
the old address (snapshotted on-chain), but future payouts go to the
new wallet. Document this in user-facing terms.

### tRPC procedures

Reviewed every router (`packages/api/src/routers/*.ts`):

| Router | Critical procedures | Auth checks | Verdict |
|---|---|---|---|
| `user` | `me`, `update`, `delete` | `protectedProcedure` everywhere. `delete` cascades to soft-delete + tombstones `privyId`. | ✅ |
| `job` | `create`, `update`, `delete`, `list` (public) | `clientProcedure` for mutations, `publicProcedure` for `list`. Mutations re-verify ownership via `clientId === ctx.user.id`. | ✅ |
| `proposal` | `create`, `accept`, `reject`, `withdraw` | `freelancerProcedure` for create. `accept` uses CAS (`UPDATE … WHERE status='pending'`) — race-safe against double-accept. | ✅ |
| `contract` | `fundEscrow`, `submitWork`, `approveWork`, `requestRevision`, `cancelContract`, `raiseDispute` | Role + status checks on every mutation. On-chain verification on `fundEscrow` + `approveWork`. | ✅ |
| `service` | `create`, `update`, `delete`, `buy` | `freelancerProcedure` for create, `publicProcedure` for read. `buy` flow inserts contract with role checks. | ✅ |
| `review` | `create` | Checks: only parties of a completed contract can review, only once each. | ✅ |
| `notification` | `markRead`, `markAllRead`, `unreadCount` | Per-user filter; user can only modify own notifications. | ✅ |
| `message` | `send`, `list` | Both parties of a contract can message; non-parties can't read. | ✅ |
| `savedJob` | `toggle`, `list`, `isSaved`, `count` | Per-user. No cross-user leakage. | ✅ |
| `search` | `global` | `publicProcedure` — fine, only surfaces public data (open jobs, active services, non-deleted users). | ✅ |
| `admin` | `listDisputed`, `recordResolution` | `adminProcedure` (env allowlist + on-chain `onlyOwner` defense). | ✅ |

### Findings

| ID | Severity | Issue | Mitigation |
|---|---|---|---|
| **BE-02** | Low | `verifyEscrowFunding` accepts the FIRST log on the receipt that decodes as `EscrowFunded`. With the v2 fix, we also gate on `log.address === escrow`. If a malicious EntryPoint were ever used (it isn't), this would still resist. | Mitigation already in place (post-v2). |
| **BE-03** | Low | `approveWork.mutateAsync` runs after `fundEscrow.run` — if it errors after the on-chain tx, on-chain release succeeds but DB stays in `submitted`. Same orphan class as fund. | Already mitigated via OPERATIONS.md recovery. Long-term: add a reconcile endpoint that retries verification given a txHash. |
| **BE-04** | Low | `notify` sends in-app + email notifications. If Resend is down, the mutation could fail mid-way, leaving the DB updated but notification unsent. | Wrap notify in try/catch + best-effort — already done in most routers. Audit + fix any that throw. |
| **BE-05** | Info | Rate limits exist for `proposal.create`, `job.create`. Other write paths (`message.send`, `review.create`) have no rate limit. | Add rate limits before public launch to prevent spam. |
| **BE-06** | Info | `contracts.escrowContractAddress` is set at fund time from `getAddresses(chainId).escrow`. If the escrow address changes (redeploy), historical contracts continue to reference the OLD address — correct behaviour, but make sure `release` / `refund` flow respects this. | Frontend `useReleaseEscrow` reads from `getAddresses(chainId).escrow` (current), NOT from `contracts.escrowContractAddress` (historical). For v1 escrows that pre-date v2, release would route to the wrong contract. Pre-mainnet: drop the v1 → v2 path entirely OR add per-contract escrow address override in the hook. |

### Trust transparency — server-side never moves money

The backend NEVER:
- Calls `release()` / `refund()` / `resolveDispute()` on its own. These
  require a signature from a party or the owner (an EOA / multisig).
- Reads or stores private keys for any user wallet. Privy stores embedded
  wallet keys in their KMS; we hold no key material.
- Reads or stores the deployer key in DB. `DEPLOYER_PRIVATE_KEY` is env-
  only, used by Hardhat at deploy time, never imported into the running app.

The backend's role is strictly:
1. Verify on-chain receipts before flipping DB rows.
2. Manage off-chain content (job descriptions, messages, reviews).
3. Compute reputation scores (off-chain).
4. Email notifications.

## 3. Frontend security audit

### Reviewed surfaces

- All `apps/web/app/**/page.tsx` for input handling + auth gates
- `apps/web/hooks/use-escrow.ts` + `use-fund-escrow-smart.ts` for wallet flows
- `apps/web/components/settings/**` for wallet address display

### Findings

| ID | Severity | Issue | Mitigation |
|---|---|---|---|
| **FE-01** | Medium | `useAccount()` from wagmi can return MetaMask EOA when MetaMask is connected, even if Forj's canonical wallet is the smart wallet. Users top up the wrong address. | **FIXED**: `useCanonicalWallet` is now the single source of truth across wallet card, deposit, withdraw, and balance hooks. |
| **FE-02** | Medium | Fund flow: if backend mutation rejects after on-chain success, button becomes clickable again — user could double-fund. | **FIXED**: button disabled when `fundEscrow.status === 'success'` + explicit toast directing to support. |
| **FE-03** | Low | Optimistic toggle in `BookmarkButton` could leave UI desynced if the page refreshes mid-flight. | Acceptable — `onSettled` invalidates the query so re-fetch corrects state on next render. |
| **FE-04** | Low | Modal escape key closes the Submit Work modal even if files are uploading. Closes the user's draft. | Add an "unsaved changes" confirm if `submissionFiles.length > 0` or `submitMessage.length > 10` before allowing dismiss. |
| **FE-05** | Info | `dangerouslySetInnerHTML` used only in `ThemeScript` (theme.css inline reader). Content is static + safe. No XSS surface. | None needed. |
| **FE-06** | Info | UploadThing returns URLs the frontend embeds in image tags. Attacker can't inject script via image src — but if a malicious user uploads SVG with embedded `<script>`, it could XSS another user viewing the file. | Either: restrict UploadThing to non-SVG image types, or serve SVGs via a `Content-Disposition: attachment` header that prevents inline rendering. Add to `lib/uploadthing/server.ts`. |
| **FE-07** | Info | `pnpm-lock.yaml` is committed. Good for reproducibility. No dev dependencies exposed at runtime via `next.config.ts` `transpilePackages` — only our own `@forj/*` packages. | None. |

### Address handling

Every place an address is displayed:
- Stored as `0x` + 40 hex chars (validated by `hex0x` regex on backend).
- Truncated for display (`0x1234…abcd`) only in non-critical UI surfaces.
- Full address always available via "Copy" button + Basescan link.

No place where the user is asked to type/paste an address back has a
silent truncation. ✅

## 4. Operational security

### Environment variables

`.env` contains the following sensitive values:
- `DATABASE_URL` — Neon connection string with creds. **Compromise**: full
  DB read/write. Mitigation: rotate quarterly; consider Neon's
  read-replica + IAM-style auth when available.
- `PRIVY_APP_SECRET` — Privy server-side token signer. **Compromise**:
  attacker can mint valid sessions for any user. Mitigation: rotate in
  Privy dashboard if leaked; treat as a master credential.
- `DEPLOYER_PRIVATE_KEY` — owner of ForjEscrow (until multisig
  migration). **Compromise**: attacker can pause fund, change feeRecipient,
  resolve disputes. Mitigation: migrate to multisig BEFORE mainnet.
- `RESEND_API_KEY`, `UPLOADTHING_TOKEN`, etc. — limited blast radius;
  rotatable.

`.gitignore` covers `.env*` (verified). The push to GitHub did NOT
include any of these.

### Audit checklist before mainnet

- [ ] Multisig deployed on Base mainnet
- [ ] Multisig accepts ownership of ForjEscrow (`acceptOwnership()`
      called from multisig itself, not from EOA)
- [ ] `feeRecipient` migrated to multisig (via `setFeeRecipient`)
- [ ] Deployer EOA private key rotated / decommissioned
- [ ] Pimlico paymaster funded with ~$20 ETH on Base mainnet
- [ ] Pimlico sponsorship policy created for mainnet with new escrow address
- [ ] Privy app moved to production mode (separate `appId` for mainnet
      so test users don't accidentally bridge)
- [ ] Sentry / error tracking enabled
- [ ] DNS pointed at production deploy (Vercel)
- [ ] Public-facing audit (paid or community) on ForjEscrow.sol
- [ ] Bug bounty program (e.g. Immunefi) — even a small one signals
      commitment to security culture
- [ ] Privacy policy + ToS lawyer-reviewed
- [ ] Backup recipient documented if primary multisig keys are lost

### Incident response

If a critical vulnerability is reported:
1. Pause funding: owner calls `pause()` on escrow.
2. Existing escrows remain releasable (withdrawals never paused).
3. Communicate via in-app banner + email blast.
4. Deploy patched contract.
5. Migrate users to new contract at their pace (no force-migration; let
   users settle existing escrows first).

If a private key is leaked:
1. Move ownership IMMEDIATELY to a freshly generated multisig.
2. `setFeeRecipient` to a fresh address.
3. Sweep accumulated fees from old recipient to new recipient (if old
   address is still controllable).
4. Rotate all other env credentials as defence in depth.

## 5. Performance findings

Not security but worth tracking:

| ID | Issue | Suggested fix |
|---|---|---|
| **PERF-01** | All 6 i18n dictionaries are statically imported in the provider — ~20 KB in every bundle. | Lazy-load with dynamic `import(\`./messages/\${code}.json\`)` once we cross 10 languages. |
| **PERF-02** | `JobCoverFallback` SVG renders per-card with full pattern definitions. On a 30-job grid, that's 30 dot-grid pattern defs. | De-dupe via a single `<defs>` block at the page level. ~10 KB savings. |
| **PERF-03** | Notifications + messages unread counts poll every 20-30s per dashboard tab. Not aware of multi-tab. | Use BroadcastChannel API to share state across tabs of the same origin. |
| **PERF-04** | tRPC client doesn't enable batch/link by default. Each query is a separate HTTP request. | Enable `httpBatchLink` for read-only queries. Reduces request count by ~3-5x on heavy pages. |
| **PERF-05** | Job listing fetches client avatar URLs by SELECT join. For 30 jobs that's 30 user rows even if many share a client. | Materialise common client profiles in the listing select. (Marginal — Drizzle handles dedup at the JS layer if you SELECT DISTINCT client first.) |

## Sign-off

This audit was performed internally pre-launch. **It is not a substitute
for a third-party audit** before mainnet. Recommended firms for a small
Solidity audit (~$5-15K range, 2-3 week turnaround):
- Sherlock, Code4rena, Spearbit (competitive audit contests)
- Cyfrin, OtterSec, Hexens (private audits)

For a true zero-trust posture before handling real customer money,
combine: (1) internal audit (this doc), (2) external paid audit, (3)
public bug bounty (Immunefi) with at least a 30-day grace period before
opening to deposits.
